# KVUI C22 — known limitations

1. **No semantic audio validation.** A newly generated incorrect mix with fresh headers may pass all safeguards. Filenames, ETags, and timestamps are not cryptographic proof of musical content.
2. **HTTP server metadata dependency.** C22 conservatively requires a valid Last-Modified header. A legitimate cached file may be rejected if it predates the original track request, and missing or inaccurate metadata will cause a retry/failure.
3. **Clock assumptions.** The timestamp comparison uses the local client clock with a two-second tolerance. Meaningful server/client clock skew can cause false decisions.
4. **ETag semantics vary.** ETags are compared for reuse across different tracks in the same song pass; an ETag need not be a unique audio-content hash. A distinct ETag does not imply a distinct instrument.
5. **HTTP intermittency.** Some live test requests returned 503 first-byte timeouts; retries recovered the tested tracks. Network/server behavior remains outside program control.
6. **Website compatibility.** Karaoke-Version may change its download endpoints, response headers, or filename format.
7. **Limited validation scope.** Tests cover a full original-key song, three -2 guitar stems on another song, and selected three-track experiments. Comprehensive cross-song, cross-key, and multi-machine coverage is still needed.
8. **Final HTTP live-test boundary.** The explicit HTTP 200 guard was included in the final passing tests/build, but was not separately live-tested through the GUI after its addition.
9. **CLI selection report (unchanged).** When `--tracks` selects a subset, CLI completion text may list **all discovered song instruments**, even though only the requested subset was downloaded. A visible Chromium test confirmed the requested one-track output; verify actual files rather than treating the summary as a list of downloaded MP3s.
10. **Original upstream fixture and debugger metadata.** The tracked source archive retains an inherited HTML test fixture containing historical webpage session/form fields and an original debugger config with local upstream development paths. Neither was introduced by Daddidio's cumulative patch. These are flagged for maintainer review, not confirmed to be live credentials.
11. **Intermittent automatic Chromium authentication at operation boundaries.** In a November 5, 2026 KVUI C22 session, Chromium opened, logged in automatically, and closed separately at **each of three operations**: (a) opening/synchronizing the purchased-song list, (b) selecting a song to load its track details, and (c) initiating a download. **For a multi-stem download, Chromium did not reopen or require another login for each individual stem.** No manual authentication was needed, and the tester reported that song browsing and the multi-stem download completed correctly. Similar browser-window behavior had previously disappeared during the C21 investigation without a code change and later returned. The root cause is unconfirmed. Website verification responses, session reuse, and KVUI fallback logic are possible contributors; **time of day, server load, and excessive requests have not been established as causes**. These automatic windows are distinct from intentionally selecting Chromium as the download method. This is an intermittent usability issue, not an observed stem-download failure. Preserve sanitized diagnostics for maintainer investigation.
12. **Distribution review.** The source retains the original MIT License and attribution. Static source/patch review found no contributor credentials or private Windows paths in the added code, but this is not an exhaustive security audit. Confirm the preferred upstream sharing procedure.

The previously verified C20 executable remains preserved privately as a fallback; it is not published in this GitHub branch.
